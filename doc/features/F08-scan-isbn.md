# Feature: F08 — Bibliothèque : scan du code-barres EAN-13 à la caméra

## Overview
Dans le formulaire d'un livre (création et modification), un bouton « Scanner » à côté du champ ISBN ouvre une modale (`UModal`) avec l'aperçu de la caméra (caméra arrière demandée en priorité). Dès qu'un code-barres EAN-13 de livre (préfixe 978 ou 979, clé de contrôle correcte) est lu, le téléphone vibre (si possible), la modale se ferme en arrêtant la caméra, un toast « Code-barres lu » s'affiche, le champ ISBN est rempli et la recherche Google Books de F07 est lancée automatiquement (même composable `useGoogleBooksLookup`, donc même endpoint et même limiteur de 10 recherches/min par membre). Un code-barres qui n'est pas celui d'un livre est ignoré avec un message discret. Si la caméra est indisponible (contexte non sécurisé, refus, aucune caméra, erreur), un message français l'explique et la saisie manuelle reste possible. En repli, « Prendre une photo du code-barres » ouvre l'appareil photo (ou la galerie) et décode l'image dans le navigateur ; aucune image n'est envoyée au serveur.

## Out of scope
- Scan en continu de plusieurs livres à la suite.
- Scan pour les outils (Garage).
- Codes ISBN-10 imprimés (seul l'EAN-13 du code-barres est lu), EAN-5 de prix, autres formats (QR, UPC…).
- Toute modification côté serveur : la validation ISBN et la recherche Google Books existent (F06, F07).
- Playwright avec caméra (impossible de manière fiable en CI).

## Acceptance criteria
- [x] AC1 (Vitest, validation): Given une chaîne lue, when on la valide, then seuls 13 chiffres commençant par 978 ou 979 et dont la clé de contrôle EAN-13 est juste sont acceptés (espaces autour retirés) ; un EAN-13 valide d'un autre produit (ex. 3017620422003), une clé fausse, une longueur différente, des lettres ou un ISBN-10 sont refusés.
- [x] AC2 (Vitest, détecteur): Given un navigateur avec `BarcodeDetector` natif qui gère `ean_13`, when on crée le détecteur, then c'est le natif (formats `['ean_13']`) et le polyfill n'est pas chargé ; given l'absence du natif (Safari iOS) ou un natif sans `ean_13`, then le polyfill `barcode-detector` est importé à la demande et configuré pour charger `zxing_reader.wasm` depuis notre build (jamais depuis un CDN).
- [x] AC3 (Vitest, scanner): Given la modale ouverte et une caméra disponible, then `getUserMedia` est appelé avec `video.facingMode` idéal `environment` sans audio et le flux est affiché dans une `<video>` muette `playsinline` ; when le détecteur lit un EAN-13 de livre, then l'événement `detected` est émis une seule fois avec l'ISBN, toutes les pistes sont arrêtées, la modale se ferme et `navigator.vibrate` est appelé s'il existe.
- [x] AC4 (Vitest, scanner): Given le détecteur qui lit un code non-livre, then rien n'est émis, la caméra continue et un message discret « Ce code-barres n'est pas celui d'un livre… » s'affiche ; une lecture valide ensuite est émise normalement.
- [x] AC5 (Vitest, scanner): Given `navigator.mediaDevices` absent, then un message français explique que la caméra n'est pas disponible (connexion sécurisée HTTPS nécessaire) et la saisie manuelle reste possible ; given une permission refusée (`NotAllowedError`), then « L'accès à la caméra a été refusé… » ; given aucune caméra (`NotFoundError`/`OverconstrainedError`), then « Aucune caméra n'a été trouvée… » ; given une caméra occupée (`NotReadableError`) ou une autre erreur, then un message français générique ; given l'échec du chargement du lecteur, then « Le lecteur de code-barres n'a pas pu se charger… » et les pistes sont arrêtées ; aucun événement n'est émis.
- [x] AC6 (Vitest, scanner): Given la caméra ouverte, when on ferme la modale ou on démonte le composant, then toutes les pistes sont arrêtées et le détecteur n'est plus appelé ; given un flux obtenu après la fermeture (permission accordée tardivement), then ses pistes sont arrêtées aussitôt.
- [x] AC7 (Vitest, repli photo): Given la modale, when on choisit une photo via « Prendre une photo du code-barres » (`accept="image/*"`, `capture="environment"`), then elle est décodée par le même détecteur dans le navigateur ; un EAN-13 de livre est émis (et la caméra arrêtée) ; un code non-livre affiche le message discret ; aucun code affiche « Aucun code-barres lisible sur cette photo… » ; rien n'est envoyé au serveur (`fetch` non appelé).
- [x] AC8 (Vitest, BookForm): Given le formulaire de création ou de modification, when on clique « Scanner », then la modale s'ouvre ; when le scanner émet un ISBN, then le champ ISBN est rempli et exactement une requête `GET /library/google-books?isbn=<isbn>` part ; le résultat préremplit le formulaire comme en F07 (encart de conflit compris en modification).
- [x] AC9 (build): Given `npm run build`, then le scanner (polyfill et `.wasm`) est dans des fichiers séparés chargés à la demande (absents du point d'entrée `app.ts`), `zxing_reader.wasm` est émis dans `public/build/assets`, et aucun fichier du build ne contient d'URL de CDN de code (jsDelivr, unpkg, cdnjs, esm.sh, Skypack, jspm) ; la vérification fait partie de `npm run build` et échoue sinon.
- [x] AC10: Given le code, when on lance `composer test`, `composer lint`, `npm run test`, `npm run lint`, `npm run build`, then tout passe, et la CI est verte.

## Technical approach
1. **Bibliothèque** : `barcode-detector` (3.2.x, polyfill/ponyfill de l'API standard `BarcodeDetector`, basé sur `zxing-wasm` ; ~250 Ko non compressé pour le JS du paquet + `zxing_reader.wasm` ~0,95 Mo, publié chaque mois, dernière version novembre 2026). Comparée à `@zxing/browser` (0.2.x, port JavaScript de ZXing, ~5,8 Mo dépaquetés avec `@zxing/library` 11,9 Mo, rythme de publication plus lent, API propre au lieu du standard, décodage en JS moins performant sur les EAN abîmés). Choix : `barcode-detector`, car il suit l'API standard (le code fonctionne à l'identique avec le natif d'Android Chrome), il est activement maintenu et zxing-cpp (WebAssembly) lit mieux les codes 1D. Une seule dépendance ajoutée (`zxing-wasm` en est une dépendance transitive).
2. **Pas de CDN** : par défaut `zxing-wasm` télécharge le `.wasm` depuis `fastly.jsdelivr.net`. On importe `zxing-wasm/reader/zxing_reader.wasm?url` (Vite émet le fichier avec empreinte dans `public/build/assets`) et on appelle `setZXingModuleOverrides({ locateFile })` avant de créer le détecteur. En défense supplémentaire, un petit plugin Vite (dans `vite.config.ts`) remplace l'URL jsDelivr par défaut du module `barcode-detector` au build (le build échoue si le motif n'est plus trouvé, pour qu'une mise à jour de la bibliothèque ne passe pas inaperçue). `scripts/check-build-no-cdn.mjs`, enchaîné à `vite build` dans `npm run build` (donc exécuté en CI et dans l'image Docker), échoue si un fichier du build contient un hôte de CDN de code ou si le `.wasm` n'est pas émis. Les hôtes Iconify présents par défaut dans le bundle depuis F01 (jamais appelés : icônes embarquées) ne sont pas dans la liste.
3. **Chargement à la demande** : `resources/js/support/library/barcodeDetector.ts` (`createBookBarcodeDetector()`) n'importe le polyfill (et l'URL du `.wasm`) que par `import()` dynamique, appelé à l'ouverture de la modale ; natif préféré quand il gère `ean_13` (pas de téléchargement du `.wasm` sur Android Chrome).
4. **Validation** : `resources/js/support/library/bookBarcode.ts` (`bookIsbnFromBarcode(raw): string | null`) : 13 chiffres, préfixe 978/979, clé EAN-13 (poids 1/3, `(10 − somme mod 10) mod 10`). Le serveur revalide l'ISBN (règle `Isbn` de F06).
5. **Composant** `components/Library/IsbnScannerModal.vue` (`v-model:open`, événement `detected(isbn)`) : à l'ouverture, vérifie `navigator.mediaDevices?.getUserMedia`, demande `{ video: { facingMode: { ideal: 'environment' } }, audio: false }`, charge le détecteur, attache le flux à une `<video muted playsinline autoplay>`, puis interroge le détecteur toutes les 200 ms (`setTimeout`, une seule détection à la fois). Un jeton de session ignore toute réponse arrivée après la fermeture (flux tardif arrêté aussitôt). Arrêt de toutes les pistes à la fermeture, au démontage et après une lecture. Messages d'erreur selon `DOMException.name`. Repli photo : `UFileUpload` (slot par défaut avec un `UButton`, attributs `accept="image/*"` et `capture="environment"` transmis à l'input), le `File` est passé directement à `detect()` (un `Blob` est une source valide de l'API), puis le modèle est remis à `null`.
6. **BookForm** : bouton « Scanner » (`i-lucide-scan-barcode`) entre le champ ISBN et « Rechercher » ; à `detected`, `form.isbn = isbn`, toast « Code-barres lu », puis `searchGoogleBooks()` (une seule recherche ; si une recherche est déjà en cours, elle n'est pas doublée).
7. Tests Vitest : `bookBarcode.test.ts`, `barcodeDetector.test.ts` (polyfill simulé par `vi.mock`), `IsbnScannerModal.test.ts` (`getUserMedia`, pistes et détecteur simulés, module détecteur mocké), `BookForm.scanner.test.ts` (scanner simulé par le module détecteur et `fetch` simulé).

Hypothèses : la recherche Google se lance même si titre/auteur sont déjà saisis (l'encart de conflit de F07 protège la saisie) ; le toast sert de « retour visuel » puisque la modale se ferme aussitôt ; le repli photo est toujours proposé dans la modale (utile aussi quand la mise au point de la caméra est mauvaise), pas seulement en cas d'erreur ; le contexte sécurisé est exigé par le navigateur : en production derrière HTTPS (F14), en local via `localhost`.

Risque : nginx doit servir `.wasm` en `application/wasm` (présent dans `mime.types` des images nginx récentes) ; sinon Emscripten se replie sur `WebAssembly.instantiate` sans streaming, plus lent mais fonctionnel.

Notes d'implémentation :
- `zxing-wasm/reader/zxing_reader.wasm?url` est importé depuis la dépendance transitive de `barcode-detector` (même version, une seule copie dans `node_modules` avec npm) : aucune deuxième dépendance déclarée.
- Le plugin Vite ne s'applique qu'au build : en `npm run dev`, Vite préempaquette la bibliothèque sans lui, mais l'override `locateFile` reste actif.
- Le `File` choisi par `UFileUpload` arrive enveloppé dans un proxy réactif de Vue, que les décodeurs natifs refusent : `shallowRef` + `toRaw()` avant `detect()` (couvert par un test).
- Vérification manuelle dans Chrome headless (spécification Playwright temporaire, non versionnée) : caméra simulée (`--use-fake-device-for-media-stream` + vidéo d'un EAN-13 généré) et repli photo (code livre et code non-livre) décodés par le polyfill, `.wasm` chargé depuis `127.0.0.1/build/assets`, aucune requête vers un autre hôte.
